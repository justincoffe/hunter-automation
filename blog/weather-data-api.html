Weather Data API Without an API Key: Current, Forecast, and Historical Conditions

A practical guide to getting current conditions, hourly and daily forecasts, and recent history for any location as structured data — no API key, no signup, pay per result.

Weather is one of those inputs that sneaks into a surprising number of products. Energy traders model demand on it. Logistics companies route around it. Farmers schedule around it. Retailers price against it. And a whole generation of apps and AI agents want to say "what's the forecast for this city?" without someone hand-typing a location into a weather widget.

The data is free and public — the awkward part has always been access, and specifically the API key you need to get at it.

The API-key problem

Most weather providers gate their data behind a signup:

  • OpenWeatherMap requires an account and an API key, and its free tier caps calls per minute and per month. The moment you poll more than a handful of cities, you're on a paid plan.
  • Historical data is almost always the paid tier. The free plans give you current + forecast; the moment you want "what was the weather in São Paulo last week," you're upgrading.
  • Enterprise vendors (Weather.com, AccuWeather, Tomorrow.io) are built for sales cycles, not for a script that needs 200 cities tonight.

Open-Meteo is the exception — a free, keyless aggregator that serves current, forecast, and historical weather over a plain HTTP API. It's genuinely good data. The remaining work is integration: geocoding city names to coordinates, parsing the response, and shaping it into one clean record per location.

The pay-per-result option

A pay-per-result weather API wraps that integration for you. You pass a list of locations (city names like "São Paulo" work — geocoding happens automatically, or you can pass explicit lat/lon), and you get back one structured record per location with: current conditions (temperature, humidity, wind, precipitation), an hourly forecast, a daily forecast, and optionally the last several days of history. It runs on Open-Meteo, so there's no key and no account on your side — you call it the same way you call any Apify actor.

A quick cost sanity check

Pricing is per location at $0.001, with a negligible per-run start fee. A thousand locations cost a dollar. A daily refresh of 500 cities — more than most products need — costs fifty cents a day, roughly $15 a month. Compare that to an enterprise weather contract or the engineering time of geocoding and parsing on your own, and the pay-per-result API wins for the common case: automated, multi-location snapshots.

Where weather data earns its keep

  • Demand and pricing models. Energy, retail, and logistics teams correlate sales/demand with temperature and precipitation.
  • AI agents and assistants. Give an LLM a compact current-conditions + forecast block for a location instead of a raw API dump.
  • Agriculture and field ops. Frost, rain, and heat thresholds against historical data drive irrigation and spraying decisions.
  • Travel and scheduling apps. "Weather at destination on arrival day" is a lookup, not a feature you hand-build.
  • Infrastructure monitoring. Flag extreme conditions at sites where equipment is weather-sensitive.

When to build your own instead

Be honest about the edges. If you need hyper-local radar imagery, minute-by-minute observations from a specific weather station, or decades of reanalysis for climate science, that's a specialized dataset — go to the vendor who owns it. For current conditions, hourly/daily forecasts, and a few days of history across many locations, a pay-per-result API is the cheapest correct answer.

Tips that will save you time

  • Batch locations per run. The actor takes a list, so a single scheduled run can refresh every city you track — don't fire one request per city.
  • Prefer explicit coordinates when you have them; city-name geocoding is convenient but coordinates remove ambiguity (there's more than one "Springfield").
  • Store history yourself. Each run gives you recent past days; append them to your own store so you build up a longer local history over time.
  • Normalize units once at ingest — decide on Celsius/Fahrenheit and km/h vs m/s before anything downstream reads the data.

The bottom line

If you need current weather, forecasts, and recent history across many locations on a recurring basis, a keyless pay-per-result API is the cheapest correct answer for most jobs. It's boring infrastructure that works — and that's exactly what you want in something you'll call every hour.
