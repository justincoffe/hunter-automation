Custom Web Scraping Service: When Off-the-Shelf Tools Fail (and What to Spec Instead)

Every scraper is easy until the third page. Page one has clean HTML and a predictable URL pattern. Page two has a pagination scheme. Page three requires a login, a CSRF token, and a challenge that appears only after your third request from the same IP address. That's the moment generic tools stop working and a custom scraping service starts earning its fee.

Why generic tools fail

The off-the-shelf options — browser extensions, no-code scrapers, point-and-click tools — are built for the easy 80%. They break on the hard 20%:

  • JavaScript rendering. Many sites are empty shells until client-side JavaScript runs. A plain HTTP request returns a blank body.
  • Authentication. Login forms, session cookies, CSRF tokens, and two-factor flows are different on every site.
  • Anti-bot defenses. Cloudflare, rate limiting, and browser fingerprinting will block a naive scraper within a handful of requests.
  • Inconsistent markup. The same product card can appear in three different HTML structures across a single category page.
  • Scale and reliability. Retries, backoff, proxy rotation, and the ability to resume a failed run all matter once you're pulling thousands of records instead of ten.

A custom scraping service handles these because it's written for your specific target, not for a general case.

What a custom scraper actually delivers

You're not paying for a one-time data dump. A proper job delivers four things:

  1. Working code you can run again — not a CSV that's stale in a week.
  2. Documentation — how to run it, what each output field means, and any known quirks.
  3. Sample output so you can verify the data shape before you pay.
  4. Error handling — a defined behavior for when the site changes, a request fails, or the target blocks you.

If someone offers you scraped data with no script and no docs, you're buying a snapshot, not a scraper. That's fine if you need the data exactly once. It's a problem if you need it every month.

How to write a spec that gets you clean data

The single biggest reason scraping projects go sideways is a vague spec. A good one answers these questions:

  • What are the exact source URLs? List them. "All of site X" is not a source list.
  • What fields do you need? Name them precisely. "Price" versus "price, currency, timestamp, and availability status" are very different asks.
  • What's the output format? CSV, JSON, a database table? Define the columns.
  • How fresh does the data need to be? One-time, daily, or on-demand?
  • What are the edge cases? Out-of-stock items, missing fields, pagination limits, deleted pages.
  • What's the volume? Ten pages or ten thousand changes the architecture entirely.

A clear spec lets the work be priced fixed rather than hourly. When the scope is ambiguous, you pay for discovery. When it's crisp, you get a fixed quote and a clean handoff.

One more thing worth putting in the spec: cleaning. Raw scraped data is rarely clean — prices come back as strings with currency symbols, dates in three different formats, names with stray whitespace. Agree up front on whether cleaning and normalization are part of the job or on you. If it's not specified, assume you'll get raw text and spend your own weekend normalizing it.

A note on doing this the right way

Scraping is legal in most places, but it has boundaries. Check the target site's terms of service and robots.txt, respect rate limits, and don't collect personal data you have no business holding. A reputable scraping service will raise these questions itself. If the person you're hiring never mentions them, that's a red flag — it means they're either inexperienced or indifferent to getting you into trouble.

What it costs, and why fixed price matters

Fixed-price scraping means the risk of "how hard will this actually be" sits with the person doing the work, not with you. You agree on fields, format, and volume; you get a number; you pay when the sample output matches the spec. If the site turns out to be a nightmare, that's priced in — you don't get a surprise invoice at the end of the month.

When to just use an API instead

Not everything needs custom work. If the target site has a public API or an RSS feed, use it — it's more stable and cheaper than scraping. And if you only need the text content of ordinary pages, a page-to-Markdown API costs a fraction of a penny per page. Custom scraping is for when those paths don't exist and you still need the data.
